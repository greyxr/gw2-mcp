# Simplified GW2 MCP Server

## Purpose and scope

Build a small, local, read-only Guild Wars 2 MCP server in Go. Its initial purpose is to inspect an account, locate stored items, and estimate Trading Post costs or proceeds. This document is sufficient for another agent to understand, reproduce, and maintain this implementation without conversation history.

The server exposes exactly twelve tools:

1. `account_overview`
2. `list_characters`
3. `get_items`
4. `get_currencies`
5. `find_item`
6. `find_items`
7. `get_character_crafting`
8. `get_market_prices`
9. `quote_trade`
10. `search_recipes`
11. `get_recipes`
12. `get_account_recipes`

Responsibilities:

- `main.go`: environment configuration, stderr logging, signal cancellation, and starting the stdio server.
- `gw2/client.go`: HTTP requests, authentication, account overview, characters and their crafting disciplines, public item and currency metadata, recipes, and account-unlocked recipe IDs.
- `gw2/inventory.go`: single- and multi-item storage search with explicit source coverage.
- `server/server.go`: twelve typed MCP tool registrations, input checks, location pagination, and public best-price output.
- `server/market.go`: market-depth quoting, fee estimates, and checked integer-copper arithmetic.

The server exposes composable API actions, not an automated crafting planner or recipe-tree optimizer. It does not yet answer multi-stage legendary crafting comparisons by itself.
It also exposes the `aurene_fang_or_weight` MCP prompt, an analysis workflow for a host agent comparing direct Weight crafting with crafting and selling Fang to fund Weight. See `CRAFTING_WORKFLOW.md` for the current target, accounting rules, market scenarios, acceptance cases, and data gaps. This prompt does not calculate a comparison or fetch external acquisition data itself.
Before handoff, exercise the actual MCP stdio surface, including all twelve tools and all four quote modes. Do not print the key or place trades.
Any expansion beyond these defined tools requires a new user decision.

## Technology and structure

- Go 1.25 or newer; module name `gw2mcp`.
- Official MCP Go SDK: `github.com/modelcontextprotocol/go-sdk`, pinned to `v1.8.0`.
- Standard-library HTTP, JSON, logging, synchronization, and arithmetic.
- Local MCP transport over stdin/stdout.
- One process and one executable. No framework, ORM, or separate service.
- A mutex-protected, process-local cache of requested public item metadata only. No full item catalog download, account cache, or disk persistence.

## Credentials, launch, and safety

The executable reads the key from `GW2_API_KEY`. `run.sh` loads the project-local `.env` only when that environment variable is absent or empty, then executes `bin/gw2-mcp`. An explicitly supplied environment key takes precedence. `.env` uses shell assignment syntax and should be owner-readable/writable only (`0600`). An existing local temporary key must be preserved, not copied into this document or source.

- Never accept the key in MCP tool arguments.
- Never put it in URLs, logs, error text, fixtures, or committed configuration.
- Only issue HTTP GET requests to the official GW2 API.
- Attach the bearer key only to account, character, and token-information requests, not public metadata/commerce requests.
- Refuse redirects. Redact the configured key from returned HTTP/transport errors.
- Reserve stdout for MCP. Send application logs to stderr.
- Missing keys fail private tools clearly; public tools can still run.
- The server never buys, sells, lists, cancels orders, collects delivery, crafts, or moves items. All trading modes below are estimates, not execution commands.

`.env` and generated binaries are ignored. There is no application database or credential persistence beyond the user-managed environment file.

## GW2 API client contract

Base URL: `https://api.guildwars2.com`.

Use schema version `2025-08-29T01:00:00.000Z` in the `v` query parameter. Add it centrally in the request helper when absent. The helper accepts root-relative API paths with or without a leading slash; it is not exposed as a generic MCP endpoint tool. Reject absolute URLs and dot-path traversal.

Use a 30-second HTTP timeout and propagate context cancellation. Only HTTP 200 is success; in particular, HTTP 206 must not silently become complete data. Bound error-body reads and return sanitized errors. Do not add retry machinery in this initial implementation.

Public methods in `internal/gw2`:

```go
NewClient(key string) *Client
(*Client).Get(ctx context.Context, path string, out any) error
(*Client).Overview(ctx context.Context) (Overview, error)
(*Client).Characters(ctx context.Context) ([]string, error)
(*Client).Items(ctx context.Context, ids []int) ([]Item, error)
(*Client).FindItem(ctx context.Context, itemID int) (FindResult, error)
(*Client).FindItems(ctx context.Context, itemIDs []int) (FindItemsResult, error)
(*Client).CraftingForCharacter(ctx context.Context, name string) ([]CraftingDiscipline, error)
(*Client).SearchRecipes(ctx context.Context, outputItemID, ingredientItemID int) ([]int, error)
(*Client).Recipes(ctx context.Context, ids []int) ([]Recipe, error)
(*Client).Currencies(ctx context.Context, ids []int) ([]Currency, error)
(*Client).AccountRecipes(ctx context.Context) ([]int, error)
```

Use only the fields needed by these tools. Item IDs and currency IDs are different namespaces; wallet values are in their native currency units. Wallet currency ID `1` is coin, measured in copper.

## MCP tools and output contracts

Inputs are JSON objects. The SDK returns structured tool output as an object with a `data` member; tool failures use MCP error results. These are live observations, not atomic account snapshots or execution promises.

### `account_overview`

Input: `{}`.

Fetch `/v2/account`, `/v2/tokeninfo`, and `/v2/account/wallet`. Permissions come from the token-information object's `permissions` field; there is no `/v2/account/permissions` endpoint.

Return `id`, `name`, `permissions`, and `wallet` entries containing currency `id` and `value`. If a required request fails, return an error rather than fabricating a complete overview. The client can then use the error to correct key permissions.

### `list_characters`

Input: `{}`.

Fetch `/v2/characters` and return the character-name array. Do not fetch builds, equipment, achievements, or all character details for this tool.

### `get_character_crafting`

Input example: `{"character_name": "My Character"}`.

Fetch `/v2/characters/{escaped-name}/crafting` and return that character's crafting disciplines, ratings, and active status. Requires the character API permission. This reports crafting access and levels, not recipe unlocks or material availability.

### `get_items`

Input example: `{"item_ids": [19721]}`.

Accept 1–200 unique positive IDs. Fetch missing entries using `/v2/items?ids=...`; retain only requested public metadata in memory. Return item `id`, `name`, `description`, `type`, `rarity`, and `flags`. An omitted requested item is an error, not an empty metadata record.

This tool resolves IDs to metadata; it does not implement item-name search or download the complete catalog.

### `get_currencies`

Input example: `{"currency_ids": [1]}`.

Accept 1–200 unique positive currency IDs and fetch `/v2/currencies?ids=...`. Return direct public metadata fields `id`, `name`, `description`, and `icon`. Currency IDs use a distinct namespace from item IDs; pass them only to currency APIs and do not use `get_items` to resolve them.

### `search_recipes`

Input: exactly one positive `output_item_id` or `ingredient_item_id`.

Fetch `/v2/recipes/search?output={output_item_id}` or `/v2/recipes/search?input={ingredient_item_id}`. Return matching recipe IDs. This is a direct search and does not traverse crafting chains.

### `get_recipes`

Input example: `{"recipe_ids": [123, 456]}`.

Accept 1–200 unique positive recipe IDs and fetch `/v2/recipes?ids=...`. Return recipe output, disciplines, minimum rating, flags, and typed ingredients (`Item`, `Currency`, or `GuildUpgrade`) with IDs and counts. This tool returns recipe data without resolving ingredient metadata or calculating costs.

### `get_account_recipes`

Input: `{}`.

Fetch `/v2/account/recipes` and return unlocked recipe IDs. Requires the API key's `unlocks` permission. This is optional, account-specific data; it is not the full recipe catalog and an unlocked recipe does not guarantee current craftability.

### `find_item`

Input example: `{"item_id": 19721, "offset": 0, "limit": 50}`.

Search these sources:

- `/v2/account/bank`
- `/v2/account/materials`
- `/v2/account/inventory` (shared inventory)
- `/v2/characters`, then `/v2/characters/{escaped-name}/inventory` for each character's bags

Aggregate matching quantities by bank, material storage, shared inventory, or character bags. Sort locations deterministically. Character names must be path-escaped.

Return:

- `item_id`
- `observed_total`: total observed across the searched sources, independent of pagination
- `complete`: whether all sources in this tool's scope were successfully read
- `sources`: source names with `ok` or `error`, plus sanitized error information
- `locations`: the requested page of location/count pairs
- `offset`, `limit`, and `location_count`

Default limit is 50, maximum 200; offset must be nonnegative. Source failures preserve successful observations but set `complete=false`. In that case `observed_total` is a lower bound, not proof of full account ownership. A complete search returning zero means none was found within this defined scope.

This search excludes equipment, socketed upgrades, legendary-armory entitlements, guild storage, Trading Post delivery, and pending orders. It does not establish whether an owned instance can be sold or consumed.

### `find_items`

Input example: `{"item_ids": [19721, 19722]}`.

Accept 1–200 unique positive item IDs. Search bank, materials, shared inventory, and character bags, reading each source once for the batch. Return one entry per requested item with `observed_total` and sorted locations, plus shared source statuses and `complete`. Failed sources preserve successful observations; totals are lower bounds when `complete` is false. This covers the same scope and exclusions as `find_item`.

### `get_market_prices`

Input example: `{"item_ids": [19721]}`.

Accept 1–200 unique positive IDs. Fetch `/v2/commerce/prices?ids=...`, which returns an array. Return each `id` with `highest_bid` and `lowest_ask` objects containing `unit_price` and `quantity`.

These are labels for existing orders: the API's `buys` are bids and its `sells` are asks. The API quantity is aggregate side quantity, not a promise that all of it is available at the best price. Use `quote_trade` for quantity-aware depth.

### `quote_trade`

Inputs:

- `item_id`: positive item ID
- `quantity`: positive integer
- `mode`: one of `buy_instant`, `buy_order`, `sell_instant`, `sell_listing`
- `unit_price`: positive copper limit required for standing modes; omit it for instant modes

For instant modes fetch `/v2/commerce/listings/{id}`. This endpoint returns one object, not an array. Validate its item ID and presence of the selected buy/sell depth array; genuine empty arrays mean no liquidity. Walk asks lowest-first for buying instantly and bids highest-first for selling instantly. Never extrapolate beyond available depth.

For standing modes calculate at the caller's price and mark the result conditional on all submitted units filling. This is not an assertion that the game will accept the proposed order or that it will fill. Sell quotes check public item flags and reject known account-bound/soulbound-on-acquire item types; they do not certify sale eligibility of a particular owned instance.

Return `item_id`, `quantity`, `mode`, `gross`, `covered`, `unfilled`, `listing_fee_estimate`, `exchange_fee_estimate`, `delivery_proceeds_estimate`, `net_estimate`, `upfront`, `conditional_on_fill`, and warnings.

For standing modes, `covered` is the quantity assumed to fill, not observed executable liquidity. `conditional_on_fill=false` for instant modes only distinguishes them from standing orders; instant quotes remain changing-market estimates.

## Trading arithmetic

Use `int64` copper and checked multiplication/addition. Never use floating-point currency calculations. Invalid negative quantities/prices and overflowing quotes must not wrap into plausible amounts.

For purchases:

- Gross is purchase cost; no buyer fee is added.
- `upfront` and `net_estimate` equal that cost.
- A buy order commits the money; it is not an additional fee.

For sales, with gross `G`:

- Listing-fee estimate: `floor(G × 5 / 100)`.
- Exchange-fee estimate: `floor(G × 10 / 100)`.
- `upfront` equals the listing-fee estimate for both seller modes.
- `delivery_proceeds_estimate = G - exchange_fee_estimate`.
- `net_estimate = G - listing_fee_estimate - exchange_fee_estimate`.

Compute percentages without overflowing an intermediate `G × percent`. A completed sale's delivery credit differs from its economic net because the listing fee was already paid. Delivery must be collected manually in-game; no server action performs that collection.

**Fee percentages and seller timing are documented, but exact copper rounding, minimums, batch grouping, and partial-fill application have not been empirically verified.** Floor calculations are an explicit initial estimate, not a calibrated rule. Keep that uncertainty visible in every quote. Controlled user-performed trades may establish exact mechanics later; do not add a fee-experiment framework now.
